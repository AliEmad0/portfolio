لم يبدُ أخطر انحدار أداء في PitchIQ خطيرًا أثناء مراجعة الكود. احتاجت صفحة اللاعب إلى اختيار الموسم، وكان التنفيذ المباشر يقرأ `?season=` داخل مكوّن الخادم.

غيّرت هذه القراءة الواحدة نموذج تنفيذ كل صفحات اللاعبين.

## معامل استعلام حوّل الصفحات الثابتة إلى دوال

كان التنفيذ غير الآمن بسيطًا:

```tsx
export default async function PlayerPage({ params, searchParams }: Props) {
  const { id } = await params;
  const { season = '2025' } = await searchParams;
  const player = await loadPlayer(id, Number(season));

  return <PlayerProfile player={player} />;
}
```

لأن صفحة الخادم أصبحت تعتمد على معامل خاص بكل طلب، لم يعد Next قادرًا على إنتاج ملف ثابت واحد قابل لإعادة الاستخدام. تحول كل عرض إلى عمل داخل دالة. ويمكن أن يحدث الانحدار نفسه عند إدخال `useSearchParams()` في غلاف العميل من دون الحد الثابت المناسب.

في نموذج Fluid لدى Vercel يختلف الزمن الكلي عن Active CPU، لكن تكرار القراءة والتحليل والتحقق والتحويل يستهلك ميزانية CPU مباشرة. توقّف المشروع بعدما انتقل عمل كان يحدث وقت البناء إلى الطلبات.

## الملفات المحلية الكبيرة ما زالت مكلفة

لم توجد قاعدة بيانات بعيدة وبطيئة. كانت البيانات على القرص، ولذلك بدت قراءتها وقت الطلب غير مؤذية.

- `player-honours.json`: نحو ٥ ميجابايت
- `player-transfer-history.json`: نحو ٨ ميجابايت
- `market-value-history.json`: نحو ٥ ميجابايت
- `player-history-stats.json`: **١٥٫٢٨ ميجابايت**

كان الملف الأخير أوضح مثال. المقاييس الممتدة موجودة أصلًا في صفوف اللاعبين العادية. قارن التدقيق **٥٨٬٣٠٣ حقل ولم يجد اختلافًا واحدًا**. تحميل الملف يعني دفع تكلفة ١٥ ميجابايت من القراءة والتحليل والتحقق من دون معلومة جديدة.

```ts
// كود يبدو رخيصًا، لكنه يعمل في سياق مكلف.
export async function GET() {
  const raw = await readFile('data/player-history-stats.json', 'utf8');
  const history = PlayerHistorySchema.parse(JSON.parse(raw));
  return Response.json(buildTrivia(history));
}
```

إذا كانت نقطة النهاية غير مخزنة، يكرر كل طلب كل خطوة.

## المحاولات الفاشلة حسّنت جسم العملية لا حدّها

يساعد تخزين المحمّلات داخل العملية، لكن نسخ serverless مؤقتة وتوزيع الطلبات خارج سيطرة التطبيق. قد تجعل زيادة الذاكرة التحليل أسرع مع بقاء المعمارية الخاطئة. ونقل الكود نفسه إلى Edge قد يزيد المشكلة لأن قيود البيئة والحزمة أشد.

لم يكن السؤال المفيد «كيف نحلل ١٥ ميجابايت أسرع؟»، بل «لماذا يحتاج هذا الطلب إلى ١٥ ميجابايت؟».

## أبقِ الصفحة ثابتة وانقل التفاعل فقط

يصيّر المسار الحالي أحدث موسم بصورة ثابتة. ويغيّر اختيار الموسم عنوان URL من دون إعادة تصيير صفحة الخادم:

```ts
function selectSeason(season: number) {
  const url = new URL(window.location.href);
  url.searchParams.set('season', String(season));
  window.history.pushState(null, '', url);
  setSeason(season);
}
```

ثم يطلب الجزء التفاعلي ملفًا محدودًا ومقصودًا:

```ts
const response = await fetch(`/api/players/${playerId}/profile?season=${season}&locale=${locale}`, {
  signal,
});

const profile: PlayerSeasonProfile = await response.json();
```

تبقى الصفحة ملف SSG، ويصبح الجزء التاريخي المختار وحده عملًا عند الطلب.

## ابنِ الملخص حيث تتغير البيانات

تستخدم الخصائص التي تعمل عند الطلب حقول إثراء صغيرة موجودة على صف اللاعب:

```ts
type PlayerEnrichment = {
  trophies: number;
  awards: number;
  internationalCaps: number;
  internationalGoals: number;
  careerFee: number | null;
};
```

تحدث عمليات الربط المكلفة في خط البيانات أو أثناء النشر، فتُدفع تكلفتها مرة واحدة. وتقرأ طبقة العرض الملخص الذي تحتاجه فقط.

كما تمنع علامة الخادم تسريب المحمّلات إلى حزمة العميل:

```ts
import 'server-only';

export async function loadMarketValueHistory() {
  // للبناء فقط؛ على مسارات الطلب استخدام ملخص الإثراء.
}
```

## احمِ نموذج التنفيذ لا الناتج فقط

لن تكشف اختبارات HTML هذه المشكلة؛ الصفحة الديناميكية تعيد المحتوى الصحيح. لذلك يحمي PitchIQ بقاء مسارات اللعبة `force-static` ويمنع صفحة اللاعب من قراءة معاملات البحث على الخادم.

ويعتمد التحقق التشغيلي على بيانات المنصة:

- انسب الاستهلاك إلى المسار وبيئة التشغيل في Observability → Functions.
- لا تستنتج من غياب ترويسة أن Middleware لم يعمل.
- افصل تكلفة Middleware المرتبطة بالزيارات عن CPU الخاص بمسار معين.
- افحص التخزين على الإنتاج، لأن اختبار الوحدة لا يثبت عمل CDN أو matcher.

كان التحسين الدائم حدًا معماريًا: الصفحات الثابتة تعرض البيانات الملتزم بها، ونقاط نهاية صغيرة تخدم التفاعل، والملفات المصدرية الكبيرة لا تدخل مسار كل طلب.
