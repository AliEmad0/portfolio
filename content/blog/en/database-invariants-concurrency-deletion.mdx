Many database bugs appear only when rows move, disappear or arrive simultaneously. Rung's fixes share one principle: encode the valid state where concurrent clients cannot disagree.

## Fractional ordering eventually runs out of space

Tasks were ordered with floating-point positions and midpoint insertion. Repeated inserts between the same neighbors lost precision after roughly fifty gaps. Concurrent clients could also choose the same midpoint.

Positions became textual fractional keys with a randomized suffix and a stable tie-breaker:

```sql
select *
from tasks
where list_id = $1
order by position asc, id asc;
```

A generated key must remain strictly between its neighbors. Keys ending in a terminal zero are invalid because shortening can alter order, and a suffix must not overtake the right neighbor. Property tests generate long insertion sequences and simultaneous same-slot writes.

## Archive visibility is not authorization

Putting `archived_at is null` inside RLS made archived tasks disappear from trash and recovery flows. Authorization should decide who may read the row; the query decides whether the current view wants active or archived rows.

Archiving every descendant also stamped many rows and emitted a Realtime storm. The parent archive state is now derived where possible rather than copied through the tree.

## Deletion runs while references are disappearing

Account deletion failed with foreign-key error 23503. Activity triggers tried to record an actor while that actor was being removed; creator references used restrictive actions; an immutability trigger rejected the database's required `SET NULL`.

The trigger distinguishes reassignment from system cleanup:

```sql
if old.created_by is not null
   and new.created_by is not null
   and old.created_by <> new.created_by then
  raise exception 'created_by is immutable';
end if;
```

Activity creation checks whether its parent and actor still exist and skips audit rows generated by the parent deletion itself. “Always write an audit row” is unsafe when the subject of the audit is vanishing in the same transaction.

## Product invariants need database guards

A workspace must always have one closed status. UI validation alone loses against direct API calls and concurrent tabs.

```sql
if old.type = 'closed'
   and not exists (
     select 1 from statuses
     where workspace_id = old.workspace_id
       and type = 'closed'
       and id <> old.id
   ) then
  raise exception 'workspace requires a closed status';
end if;
```

List creation also had color defaults in four places: TypeScript arrays, SQL, an RPC and a column default. Updating the UI left new database-created lists with old colors. The regression test calls `create_list` and measures the stored row rather than asserting another copy of the expected hex values.

## Workspace identity belongs in keys

Independent foreign keys allowed a child to reference a list from one workspace and a status from another. Composite constraints make the relationship structural:

```sql
foreign key (workspace_id, list_id)
  references lists (workspace_id, id),
foreign key (workspace_id, status_id)
  references statuses (workspace_id, id)
```

## Migration tests should attack transitions

A schema test that inserts one valid row misses these failures. Useful scenarios include:

- fifty-plus inserts into one ordering gap;
- two clients choosing the same slot;
- archive → trash → restore;
- deleting an account with tasks and activity;
- removing or converting the last closed status;
- invoking defaults through both RPC and Data API;
- attempting cross-workspace foreign-key combinations.

Constraints are not defensive clutter. They are the executable definition of which states the product considers possible.
